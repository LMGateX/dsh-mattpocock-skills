# DSH 薄适配插件：职责与后续范围

## 决策

经 owner 认可，后续工作回到薄适配插件：提供固定版本的 Skills，接入 DSH 原生注册、发现、加载和调用机制；仅对已证实的宿主差异做最小兼容处理。停止扩展通用行为审计器。

本文收缩后续工程范围，不改写历史评估结果，也不自动解除既有激活或发布门槛。owner Web 激活、发布、可见性变更、新模型试验仍需另行决定。

首轮有证据的能力盘点见 [兼容性清单](COMPATIBILITY.md)，其中明确区分原生支持、条件支持、具体差异与未验证事项。

## 当前代码职责盘点

| 层次 | 文件/入口 | 职责与处理方式 |
|---|---|---|
| 运行时入口 | `src/index.ts` | 通道配置（通道集从 catalog 派生），向 `ctx.skills.registerProvider` 注册 provider；保留 |
| 运行时目录 | `src/catalog.ts` | 读取、校验和冻结生成的 Skill 元数据；保留 |
| 运行时加载 | `src/provider.ts` | `list` 按 channel 返回候选项；`get` 按需返回准确正文、调用元数据和资源目录；保留 |
| 来源与分发 | `scripts/update-source.mjs`、`scripts/verify-vendor.mjs`、静态 catalog 与 vendor | 固定来源、构建元数据及检查内容完整性；保留，不继续增加无实际需求的机制 |
| 包契约验证 | package/provider/registry 测试与 package/isolated verifier | 验证可安装性和原生注册加载契约；保留 |
| 历史行为评估 | 不在本仓库内 | 独立评估资产，不是插件运行时。为公开仓库做准备，评估器械与原始记录已于源提交 `f4e8c12` 逐字节归档到本仓库之外的私有位置，不再保留在公开仓库中；原始记录未被删除或改写，结论不变，仍为 2 次通过、1 次硬失败、总体失败 |

实际运行时入口共三个 TypeScript 文件：index 33 行、catalog 171 行、provider 251 行（本次盘点基线）。主要复杂度来自校验与外围评估，而不是另建了一套运行时调度框架。薄适配不意味着为减少行数而移除已验证的内容和路径检查。

## 明确的宿主边界

插件提供 SkillCandidate / SkillDefinition；用户 slash 手势识别和上下文注入由 DSH 原生机制负责。插件本身不解析用户消息、不实现工具调用翻译、不提供子代理调度或等待机制。

“指令可兼容”需要分开验证：

1. **入口兼容**：名称、描述、调用权限、正文与资源路径正确。
2. **语义兼容**：Skill 提及的工具、指令和流程约定能在 DSH 上执行。正文正确加载并不证明所有语义都兼容。
3. **行为效果**：特定模型在特定宿主场景中是否完成任务；不等于插件契约是否正确。

不实现通用 Shell 解析/安全策略引擎、生产代码 AST 限制器或整个 Agent 执行过程的正确性证明系统作为插件能力。已有 Phase 5 分析器不进入运行时职责。

## 简化后的验证方法

- **插件契约测试**：注册、卸载、channel、调用权限、准确正文、资源路径和包安装。
- **兼容性清单**：逐项记录原生支持、需最小映射、存在限制、未验证；所有结论标注代码或实际观察依据。
- **少量工作流冒烟验证**：代表性的用户调用、模型调用、资源读取与异步子代理流程。以原始记录、明确断言和结果检查定位问题，不构建完备证明器。任何新增真实模型试验先取得单独授权。

## 历史结论与下一步

三次活动仍为 2 次通过、1 次硬失败、总体失败；Trial 3 的早返回和缺失 review 保持原样。该观察不直接证明 Web 场景失败，也不直接证明 provider 注入失败。

首轮兼容性清单与 headless 后台子代理生命周期源码盘点已完成，见 [兼容性清单](COMPATIBILITY.md)；已确认限制也已同步至双语 README。后续仅在具体需求或已确认缺口出现时提出最小修复，并区分 DSH runtime、adapter 与上游 Skill 的责任。

历史文档收尾涉及审查、提交和推送，不构成后续工程的推送、部署或发布授权。插件仓库现在按已接受政策公开，个人对话、本机信息与原始评估材料不进入公开提交；源码分发仓库的既有隐私和不可变来源政策不变。历史评估结论及记录保留，不改写官方 Skill body。

## 已接受扩展范围：可选工作区协作控制（2026-10-05）

新增产品要求见 [协作控制规格](<WORKSPACE_WORKFLOW_CONTROLS.md>)：插件页面配置全局/按工作区的 worktree 绑定与仪器策略，生命周期、tickets/running subagents 双窗口、票进度与待裁决仪器。已接受设计采用工作区策略主视图、稀疏继承和显式保存，并要求所有仪器按持久主 session 独立实例化；同工作区不同主 session 的业务状态与窗口不混用，受管 children 归属主实例，真实共享资源锁仍有效，详见 [session 仪器](<SESSION_INSTRUMENTS.md>)。两个滑动窗口逐项释放/补入，无票研究不占 T；结果与状态变化自动注入主代理上下文，执行释放由程序回执确认，详见 [响应式消费设计](<REACTIVE_WINDOW_INSTRUMENTATION.md>)。

这明确增加了可选扩展的运行时职责：持久归属/状态、配置解析与受控容量准入。规格进一步明确：仪器不决定何时要用户裁决、票是否真的完成或暂停/取消是否业务合理；模型依据 Skill、约定和文档判断后更新仪器。保留归属/revision/幂等计数与执行程序回执，不另建业务证据 gate、风险分类器、自动审批或自定任务业务优先级。这不取消显式启用窗口的强制准入和必要行为引导，也不取消 worktree 使用/收尾的轻量引导；候选协议与用户项目约定的职责见 [引导设计](<INSTRUMENT_GUIDANCE.md>)。上文“插件本身不提供子代理调度”描述既有 Skill provider，不再用它否定 已接受的可选窗口控制需求；但仍不把完整票图/issue tracker/Git 调度器或通用行为证明器塞进该 provider。

需求已记录，机制、默认值、入口打包与强约束所需宿主 seam 尚待决定，均未实现。既有 vendor、两通道及加载优先级保持不变；研究材料不会自动启用工具、修改正在运行的插件页面或解除发布/模型试验门槛。
