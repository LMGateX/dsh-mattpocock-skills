## 1. 已确认要求与设计建议

规格要求：

- 用户在 session 内持续看到 tickets 进度；状态种类、名称与业务含义由 agent 按实际任务提供，包含“部分完成”等情况也不要求映射到固定分类。
- 待裁决事项有不会被对话滚动淹没的指示器，尤其覆盖 tickets 执行期间出现的新问题。
- 前述所有仪器绑定 session；同一工作区不同 session、不同分支拥有不同实例，状态不混用。
- 上一轮配置页建议获认可：Skills 与协作管理分开；工作区为策略主视图；全局默认＋稀疏覆盖；显式保存、显示修改影响与实际收敛状态。

下述字段、状态展示元数据、具体显示位置和工具命名仍为设计建议；业务裁决/交付规则不由仪器制定；不把本次讨论当作运行时实现或当前 GUI 修改授权。

## 2. 作用域：工作区给策略，主 session 持有实例

| 对象 | 归属 | 含义 |
|---|---|---|
| 启用开关、默认 T/S、显示偏好 | 当前 host/profile 的全局默认＋控制工作区覆盖 | 可供多个主 session 采用的策略，不是业务状态 |
| 仪器实例、票进度、待裁决、T/S 占用、工作树视图 | 持久 ownerSessionId | 同工作区独立主 session 分开存储、读取、注入 |
| 任务目标、票集合与业务状态字典 | instance 下的 workflowId | 区分同 session 的前后任务；不额外开窗口 |
| child、assignment、执行与 worktree 关联 | 显式 instance/workflow 关联 | 子代理贡献所属主会话状态，不按 child cwd 分桶 |
| 实际目录/资源 writer 排斥、integration 写锁 | 真实 worktree 身份或 Git common-dir＋integration ref | 不因 session 状态隔离而解除共享现场的安全约束 |

- 建议稳定 instrumentInstanceId 与 ownerSessionId 持久关联；controlWorkspaceId 决定策略来源，instanceId 决定账本与权限作用域。branch/ref 与 SHA 是任务及资源属性，不是实例主键。
- **本设计采用 session 实例内 T/S，而不是工作区所有 session 的合计 T/S。** 工作区设置 T=3/S=2 时，独立主 session A、B 分别管理自己的 T=3/S=2。旧草案的工作区共享业务账本/配额规则已替换。未来若需要工作区/host 总资源预算，另设独立上层限制并显式展示，不能偷偷合并这些仪器。
- 同一实例内所有 workflows、coordinators 与受管 descendants 共用 T/S。新建 child、重建 Agent、换 cwd 或换 workflowId 不开新实例、不刷新容量；独立主 session 与受管 child 的角色必须来自可信关联。
- 同一主 session 的断线、刷新、Agent dispose、重启和冷续聊恢复同一实例。切换浏览器选中 session 只切换投影，不迁移或清空状态。
- session fork/new session 建立独立实例；需要继承任务计划时显式复制/关联，不能复制活跃 leases、资源所有权或用户授权。跨实例移交票/资源需要明确交接与旧归属收敛，不靠改一个 sessionId。
- 同一 session 开展新任务时使用 workflow 分组并明确当前筛选/归档范围；不自动丢掉旧任务的待裁决、未交付或未退休义务。
- 相同外部 ticketRef 可出现在 A/B 实例，但本地票身份至少包含 instanceId＋workflowId＋localTicketId。它们不是自动共享的一份 tracker 写权限；外部写回与集成仍核验目标和权限。
- “不同 branch”只有关联信息，不是文件隔离保证：两个 session 若仍写同一个 checkout，会干扰 HEAD/index。开启并行 writer 前必须核对真实树/授权；多个实例引用同一资源时，退休检查所有 leases/引用，不能仅看自己的空闲视图。

## 3. Tickets 进度：业务状态可扩展，控制事实固定

### 3.1 状态字典由 agent 按任务声明

建议 agent 使用结构化工具声明当前 workflow 的状态字典，而非让 UI 从聊天正文抽取：

- 每种状态有稳定 statusKey、可读 label 与简要含义；排序、强调等展示信息可按任务声明，具体字段待定。
- 插件不预设业务状态全集，也不预设研究/实施/合并/验收等任务阶段。字典由 agent 根据当前任务声明并可随任务演进扩展，仅在所属 workflow 生效。
- **移除上一版固定摘要分类与强制映射建议。** GUI 的摘要和详情都按任务声明的状态及其实际票数动态展示；“部分完成”如被声明，应独立保留其名称、含义和计数，不折算为进行中、完成或其他。不通过增加更多内置枚举来处理这次纠正。
- 若需要更紧凑的摘要，由 agent 为当前任务声明哪些状态优先显示；其他状态仍可展开查看。任何可选分组都由该任务明确定义，不要求映射到插件的统一类别。
- 状态可以是单一主状态，也可以是任务声明的多状态/多轴；仪器不强制把其他状态降成 tags/blocker。按模型声明的统计口径展示：互斥分类可合计，重叠状态逐项计数并注明可能重叠，不把各计数简单相加冒充票总数。待裁决属于独立维度。
- 字典修改有 revision；状态重命名保留 key，删除被使用的状态须迁移或保留历史。

建议状态种类与报告属于业务数据，agent 有权维护；与用户拥有的配置开关、窗口容量和权限授予分开。受管 child 仅提交分配给自己的票状态，由 coordinator/明确授权的调用者维护全任务定义；服务端核验所属实例与 assignment。

### 3.2 业务判断由模型负责，仪器维护记录与计数

容量满、revision 冲突、未知执行、路径/引用不匹配等技术拒绝返回相应事实与诊断，不自动转换为票的业务 blocker、待用户裁决或新增审批。是否要找用户、如何处理这些事实仍由模型按任务约定决定。

**已接受澄清（2026-10-06）：何时需要裁决、何时完成/交付、是否暂停或取消，由 Matt Pocock Skills、用户与 agent 的约定、任务文档和模型判断决定。仪器提供能力，不制定业务标准，不额外审判或审批。**

| 信息/操作 | 谁决定 | 仪器职责 |
|---|---|---|
| 自由票状态、完成/交付、暂停/取消/reopen | agent 按任务已有约定判断并显式更新 | 保存原状态/作者/可选依据；按显式窗口意图更新 T |
| 是否提出待裁决事项、请谁裁决、是否阻塞、事项是否解决/落实 | 模型按任务约定判断并显式更新；用户也可从 UI 输入 | 登记/更新/撤回事项，展示和通知，不生成新的审批标准 |
| 执行结束与 S 释放 | 可信程序事件/完成回执 | 匹配实例、执行代次与 lease，幂等更新 S |
| 文件操作/资源释放的技术可执行性 | 真实资源/租约事实及现有宿主权限 | 核验身份、路径、所有权/引用、活跃执行，遵守 sandbox；不把业务完成标签当删除回执 |

票更新可以同时带有“继续占 T / 释放本票 T / 恢复占位”的结构化意图，或采用 agent 为当前状态字典显式声明的窗口效果；具体字段待定。这只是让模型的决定得到确定性执行，不是仪器评估是否真的完成。不能靠解析自由 label/聊天正文猜窗口效果；已明确声明的效果则可随状态更新生效，无需插件另要求集成/测试证明或用户审批。一个 T 释放即可补一个，S 仍独立。多状态/多轴的业务标签不要求互斥，但一次票窗口更新的占位意图必须明确且幂等；结构化参数冲突可返回诊断，不由仪器选取业务优先级。

旧版把 integrated_verified、插件核验交付、cancelled_approved/parked_approved 作为普遍业务 gate 的建议取消。特定 Skill/任务仍可要求这些步骤，但由模型遵循其约定，不由仪器新增或解释。理由、文档/用户消息/测试引用可保存用于回溯，但不是统一必填的证明包。

UI 展示模型提供的业务状态与处置，注明来源；不能把“已提交到仪器”包装成“插件证明业务正确”。程序执行状态单独标注。“部分完成”不自动代表任何百分比；仪器的 stale/unknown 是数据健康信息，不是新的业务类别。票总数与当前 T 占用分别统计；改变显示、刷新或执行结束不自动替模型更新业务处置。

## 4. 待裁决事项：模型主动登记，仪器持久呈现

### 4.1 提出与更新

模型认为需要裁决时调用仪器登记事项；认为已有答案、已自行处理、问题撤回或已落实时，可以按任务约定更新。仪器不扫描 blocker、失败次数、风险关键词或票状态来自动生成/升级裁决请求，不决定哪些问题必须找用户，不迫使模型为了更新状态再提一个审批。

建议记录 decisionId、instanceId、workflowId、关联 tickets（可空/多张）、提出者、问题/背景、可选选项/建议、模型标明的影响/阻塞范围、拟请的裁决者、来源引用、revision 与处置结果。具体字段待定；简单事项不要求填写一整套审批表。

- “待你裁决”计数来自模型/明确用户操作登记的受理对象与当前状态，不是仪器自己的业务判断。
- 来源使用真实消息/工具身份；无链接时保留提出记录，不虚构聊天锚点。
- 更新核验 session/assignment 归属、基本工具访问权限、revision 与幂等性，而不是核验模型的业务理由是否足够正确。
- agent 可记录其判断或对用户自然语言答复的理解，并标明 agent 更新及引用来源；UI 的真实用户选择另有真实事件归属。保留来源区别，不把 agent 调用伪装成用户亲自点击，也不禁止模型依据已有用户答复更新事项。

### 4.2 显示生命周期，而非审批 gate

可以呈现“待裁决 → 已裁决、待落实 → 已落实”，以及撤回/替代等记录。这是可用的记录/展示能力，不是强制每个事项走完的审批流程；具体业务状态和转换由模型按任务语义更新。

- 已读/隐藏只改变 UI 元数据，不自动解决事项；显式业务更新可以解决/撤回事项。
- 是否需要补问用户、是否继续执行或阻塞哪张票由模型决定；仪器可以保存这些说明，但不自动锁住业务分支，也不因用户沉默自行产生决定。
- 新事实是否使旧决定失效由模型处理，仪器保留更新历史和来源，不建立独立失效规则来反复索取裁决。
- 事项记录不授予新的 sandbox、系统权限或配置修改权；现有宿主访问控制依旧适用，不增加本插件自己的业务审批层。
- 事项没有第三个执行窗口；其状态不会直接释放 S。T 是否变化遵循模型显式票窗口更新，而非待裁决计数。

### 4.3 防止被对话淹没

按模型已登记的数据，在 session 固定位置显示“待你裁决 N”及其标明的阻塞信息；点击查看/回答，模型可消费回答并更新事项。已裁决待落实可单列，显示均可配置。

阅读、滚动、切换 session、刷新、Agent 实例释放或隐藏面板不清空记录。普通刷新合并，新登记事项可有一次温和提示；仪器不因为久未响应就升级问题或反复催促模型/用户。

## 5. GUI 与配置页分工

### 5.1 Session 页面

建议在 session 固定摘要位置显示四类仪器：

- 票进度：按当前 workflow 的状态字典动态显示各状态名称与票数；紧凑摘要不采用固定分类，展开保留全部状态、含义与票列表。模型提交的处置/可选依据与程序执行事实保留各自来源。
- 待裁决：待你裁决、阻塞相关任务、已裁决待落实。
- 双窗口：本实例 T/S 的容量、占用、空位，S 区分预留/运行/停止/未知。
- 工作树：本实例关联资源、待合并/可退休/清理失败；共享资源引用与安全限制仍可见。

列表按当前 selected session 解析 owner instance。受管 child session 显示“归属主 session X”及其 assignment 范围；不假装拥有独立满额容量。用户需能切换“当前 workflow/整个实例”范围并看清统计口径。

具体布局尚待 owner 讨论确认；后续 [位置研究](<SESSION_INSTRUMENT_PLACEMENT.md>)已静态核验安装版 header/composer/右栏席位，并区分原生紧凑贡献和缺失的完整 secondary header seam。尚未生成视觉稿、测试用户浏览器视口或实现仪器，不能把理想布局当作现成插槽。切换 session 后，异步返回须核对实例/请求代次，旧 A 快照不能落到 B 的面板。

### 5.2 插件配置页

已认可的方向：

- 区分 DSH 原生插件启停、协作管理总开关和按工作区功能开关；Skills 分发独立于管理总开关。
- 以工作区为策略主视图：全局默认、稀疏覆盖（继承/显式开/显式关）、来源与实际状态。
- 工作区容量是每个 session 实例采用的容量，不是工作区所有 session 合计预算；列表与影响预览明确显示。
- tickets 进度、待裁决的功能启用与 GUI 显示分开；owner 要求配置页提供各显示方式开关，沿用全局默认/工作区覆盖。已认可的位置默认组合、全隐藏提示与能力限制见 [显示配置](<SESSION_INSTRUMENT_PLACEMENT.md>)；具体 schema、新仪器功能启用初值与 T/S 数值默认仍待定。隐藏显示不改变账本、权限、交付或裁决义务，也不关闭主代理自动状态消费。
- draft → 修改影响预览 → 显式保存（expectedRevision）→ 已保存配置＋运行收敛状态；旧 revision 冲突拒写。
- 保存的是配置意图；effective policy 是后端计算；运行账本保存事实。GUI 不计算自己的继承、计数或释放。
- 修改工作区默认影响该工作区仍继承的实例策略，逐实例显示 draining/overcommitted/unsupported；不迁移旧 cwd，不取消票、不强杀执行。
- 同页可以按 session 查看运行详情；工作区汇总必须明确是跨实例只读汇总，不能作为任何 session 的票清单或窗口空位。
- 原生直接停用插件的处置另行验证，不能宣传为已实现安全 draining。

## 6. 自动接入、授权与恢复

- 工具通过受信任调用者 session＋持久受管关联解析 instance；远程请求核验读写权限。agent 提供的 instanceId/sessionId 仅是选择参数，不是授权凭证。
- 结构化状态声明/报告、事项提出/裁决/落实、票交付、程序执行释放、资源变化提交到所属实例账本，形成单调 revision 与通知意图。
- GUI 实时订阅与 parent 自动注入读取同一已提交投影；业务更新归属于实际提交者，host 注入确认“记录已提交/T 已按显式意图更新”，不是独立业务正确性证明，更不是执行结束回执。
- session 恢复/合法 wake 时自动带入当前进度、未裁决、已裁决待落实与 T/S/资源状态，以及已启用机制的最小协议引导；提示词未验证/项目调优及功能关闭的处理见 [引导设计](<INSTRUMENT_GUIDANCE.md>)；返回消息消费仍遵守 [相关事件有限水位 fence](<REACTIVE_WINDOW_INSTRUMENTATION.md>)，不等待 sender end。
- 裁决提交需同时保存决定与待落实/通知记录；agent 未在线或通知失败时仍保留决定，恢复后处理。具体存储/消息确认契约未验证，不宣称跨日志 exactly-once。
- 账本观测失效时显示 stale/unknown，不能用 0 或绿灯掩盖。实例归档/删除策略保留未交付、未裁决、未退休义务，具体交接/保留规则另行确定。

## 7. 未来无模型验收

1. 同工作区 A/B 独立主 session、不同 branch：票号和自定义状态相同也不串计数、事项、T/S 或树状态；同 branch 的独立 session 同样隔离业务状态。
2. A 的受管 children/嵌套 coordinator 共用 A 实例窗口；Agent dispose、刷新、冷恢复不创建新实例。fork 不复制活跃 leases/授权。
3. 自由单状态/多状态/多轴原样显示，互斥/重叠计数口径清晰；“部分完成”不被分类或猜测比例。仅更新 label 不推导窗口变化；模型显式释放 T 或声明状态窗口效果后，T 正确更新，S 不受影响。
4. 票总数与 T used 可不同；动态新增/取消改变总数可解释；跨 workflow 汇总带清晰范围。
5. 模型可提出/更新/解决/撤回事项，仪器不额外生成业务审批、分类何时必须找用户或判断业务决定；保存直接用户输入与 agent 理解更新的不同来源，旧 revision 拒写；已读/隐藏不自动解决。
6. 仪器不因 blocker/测试失败/事项超时自动制造裁决或停止业务任务；模型自行安排工作。票的业务更新可改 T，但不能改执行状态/S；消息正常消费、不等待 child end。
7. 快速切换 A/B，A 的迟到请求/通知不落到 B 面板或模型上下文；无 caller/未知关联明确拒绝或降级。
8. 配置修改按工作区策略影响各实例而不合并状态；缩容安全收敛；同一真实树/integration writer 冲突与跨实例退休检查仍有效。
9. 真正模型输入捕获到当前实例的自动进度/裁决/窗口快照；持久化失败/通知重试/离线裁决不丢决定或伪造最新状态。
