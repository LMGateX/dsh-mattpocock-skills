## 1. 推荐结论与第一阶段非目标

推荐**先兼容收敛使用语义和关注入口，再逐项转移/收尾存量**，不先破坏存储或发明另一套跟踪器。

1. 保留 put-decision action、既有字段、V1/V2 存储读取、CAS/幂等与旧记录必要更新能力；不为“新流程/旧流程”加用途枚举或按版本时间猜记录类别。
2. 新流程仅在真实需要用户作决定时登记并等待答复；普通技术选择/研究/执行报告回既有文档和任务。该职责由指导和任务约定约束，不新增运行时业务审判 gate，不能宣传程序已能识别全部自娱自乐记录。
3. 常驻输入/顶部关注位取消把 awaitingImplementationCount 称为“待落实任务数”；原始兼容字段/计数仍完整可读，不改名后伪装为真实未完成数量。推荐用低强调“记录核对”入口接住它，而不是把数值藏掉。
4. 执行与验收只由既有任务承载一份状态；decision 可以有指针，但不独立轮询/回填任务完成率，不根据票状态词自动清标记。
5. 存量逐项复核后可明确“落实责任已移交任务”并解除旧标记；这不等于宣称业务已完成。未知、真实未决与移交失败继续保留。

第一阶段不删除 awaiting 字段/计数、不拒绝所有 agent/unspecified 旧对象、不增跨 tracker 写入器/跨域事务/永久迁移分类账，不新增模型工具或通用链接系统。可信创建时间是 UI 独立交付目标，来源/最小只读投影另按 UI 契约验证，不因本兼容方案不迁存储而略过。

## 3. 新流程与旧对象的最小操作契约

### 3.1 新用户问题与真实答复

- 创建真实待答事项时明确 pending=true、addressee.kind=user；新流程不使用 awaiting=true 作为每个问题的默认下一阶段。author 仍取认证调用者，不由模型自填。
- 收到明确答复后更新**同一** decision：问题已解决才按原约定明确 pending=false；部分答复/仍需澄清保留 pending。明确拒绝、撤回、替代或不再需要答复也可按真实原因结束待答，不把它们伪装成批准。保留答复与依据；取消/未答/关闭不是授权，不因 result 非空自动解决。
- 对无既有兼容标记的新事项，后续行动写既有任务；不再回写第二份完成进度。
- 对旧 awaiting=true 的事项，答复更新应保留它，除非本次同时具备明确的核账/移交依据与授权；不可在普通答复保存时用新默认值顺手清旧标记。
- 存储仍允许旧 wire，过渡期不新增“所有 put-decision 都必须 addressee=user”的技术拒绝。缺省/agent/unspecified 不是用户待答队列，必要旧对象仍可读/更新；这不是继续鼓励新建普通自裁决。

### 3.2 决定 → 任务指针

- 现有本地票关联继续用 ticketIds，但它表示相关性和权限范围，不证明票已承担全部承诺，更不证明已完成。
- 落实载体若是外部 issue、其他工作流票或任务文档，使用既有 result/context 中的可读完整指针；任务端回链仅在已授权且有真实写入入口时补齐，不假定插件有 tracker 写入器。不能写回时明确单向指针与限制；关键承接仍未确认就暂不清标记。references 作为本次更新来源补充，不作为唯一长期关联字段。没有机器接口就只展示声明引用，绝不冒称已验证外部状态。
- 修改 context/result 时保留已有原问题/用户答复/关键指针，核账说明不能覆盖答复。若需长期保留的答复来源仅在已授权可见的旧 Change.references，应在处置前将必要引用转录到持久 context，并明确标为本次 authored 转录；不改写原作者/recordedAt、不认证引用内容。来源已缺则写未知，不能猜测还原。任务端持有执行状态；decision 正文只说明决定和承接去向，不复制 checklist 或周期同步状态。一条决定可关联明确任务集合，但每个动作只有一份完成真值，不能为凑“一张票”再造汇总待办。
- 没有真实任务则先按既有任务流程补齐，不创造内容为空的“迁移票”来清数字；功能 OFF 不为移交自动开启 ticketProgress，也不违反既有禁止新建规则。
- 若将来确需稳定机器可解析、跨 tracker 的 typed links，再提出独立读取/写入/授权契约；首阶段不把普通引用偷偷升级成这样的能力。

### 3.3 两种保存意图分开

1. **记录用户答复**：沿用原生消息理解或显式用户编辑，实际作者如实记录，明确选择是否仍待用户回答；不能让兼容收尾假扮这个意图。
2. **登记核账处置**：由有权操作者明确修改原事项，保留必填 question/status、result 与非目标字段（status 仅在有明确业务处置时改变）；在 context 追加简短 authored 核账说明/任务去向，并带本次来源 references。显式选择本次改变的标记。它是业务声明，不是插件证明完成。

两者复用现有 put-decision，无新增 wire action；兼容 UI 可在稳定 reader 中区分操作说明与表单，不增专用聊天输入框。核账处置不要求捏造新的用户答案，也不以固定 status taxonomy 或新增通用证据审批表设 gate。字段省略保留、原修订草稿、错误保留与重新读取不变。

## 4. 关注入口的最终推荐

以下是 B 的具体 UI 细化推荐，获认可并实现后才取代旧四入口/待落实常驻规则，不能以文档草案宣称当前 GUI 已变。

| 表面 | 推荐呈现 | 不可改变的事实 |
|---|---|---|
| 输入区/顶部主摘要 | 待你裁决、票进度、T/S；不再把兼容 await 数字当用户执行待办 | pending-user 计数不变，未知不伪装 0 |
| 输入区次级入口 | 低强调“记录核对”，不合成为一个无依据的“未完成数”；有兼容未决或读取未知时可达 | 不依赖 rightPanel；复用就地只读 region，支持原生键盘与持久阅读 |
| 记录核对详情 | 明确“原待落实标记 N，不等于未完成任务”；另列非用户 pending 记录及范围/未知 | N 保持原 awaitingImplementationCount 条件；与 pending 数可重叠，不能相加 |
| 右侧详情/设置所选会话 | 用户待答与兼容核对分区；已解决/其他记录默认折叠，但全文与显式编辑可达 | 不删除账本，不让 agent/unspecified 进入用户队列，不把 false/false 全叫已用户裁决 |
| 会话列表/浏览器提醒 | 仅真实 pending-user 触发原有关注/通知 | 不为兼容 await、页数变化或单纯处置重放制造新用户问题 |

纯客户端核对清单可在同一授权完整投影上用 awaiting=true 或（pending=true 且非 user）求并集去重，但**这不是新的持久领域类别或新计数 wire**。不以创建日期/升级时间判断“旧记录”。选择以 session/instance/workflow/decision 定位，但须同时保留真实 caller、当前 scope/授权修订与撤权围栏；只在身份与授权不变时分类变化不关闭阅读，身份/授权改变应清理旧正文/草稿并重新授权。原轻量 SessionSummary 不增 await/核对正文，不为次级入口破坏轻量读取。

对所有显示位关闭的情况保持用户显示偏好，不自动强开；模型已有义务与按需授权查询仍在。未知/缺数组不能求并集变空，原摘要与明细不一致须说明而非重算真值。

## 5. 消费、通知与结论兼容

- 模型工具默认概览、分页、正文 locator 与写回执仍用 schemaVersion 2 和原预算，raw pending/awaiting 计数与续读能力保留；不能让模型因 UI 去掉强调而认为旧义务已消失。模型说明将 await 定位为“需按任务依据核对的兼容标记”，不是当前未完成任务总数。
- 活动消费保留 pending 或 awaiting 的真实当前义务直到显式处置，不用 hidden/退出注入绕过。管理 OFF 继续保留旧对象和必要收尾，不诱导新增普通 decision 或自动启用管理。
- **浏览器 episode 提醒**仍只用 pending-user 与原去重；账本变更到主代理的 notifyOwner/持久回执是另一条路径，不因 UI 改造关闭。真实 user/child 的核账业务写入可能产生 owner 通知，应如实验证，不把它假扮新用户裁决，也不为迁移偷偷静默。
- contextConclusions 继续只读兼容当前已决结果、原纳入历史与来源；不自动把所有 agent 结论删掉，也不新建 decision 作为一般记忆存储。核账说明放 context，不覆盖 result 以免改写原答复/结论。
- **清 await 也可能让原事项退出活动上下文。** [captureBusiness](<../src/runtime.ts#L189-L200>)把非 pending 且非 awaiting 记为 flags.done；[默认上下文](<../src/controls/history.ts#L128-L131>)对 done 不再默认纳入。因此 done 仅指仪器未决标记结束，不是落实完成；清标记前须确认承诺、原决定约束/必要答复指针已由真实任务/文档的有效上下文承接，或按现有显式纳入规则保留必要结论。保留既有 included 选择，不批量把旧日志全部纳入，也不擅自覆盖显式 excluded。查询页/当前工具若不暴露完整纳入设置，只能记录可见活动覆盖与未知，不能假称导出了内部 contexts 全集。
- 所有读取与每页/片/重试仍校验实际 caller、owner、instance、scope 和源修订；不把工具 locator、目标 session ID 或用户选中导航当权限。

## 6. 88 项核账：固定范围与互斥分类

### 6.1 最小采样协议

先读取目标会话授权完整当前表示或读完一致源版本的有界分页。固定 session/owner/instance/caller/scope、records revision/businessRevision/viewerRevision、采样时刻与实际摘要计数；现在的数未必仍为截图的 88。current-view-changed 或权限改变时重开，不能混页凑总量。外部任务来源不能跨系统原子固定，另记各自采样时刻和未知/受限，不冒称联合快照。

每条至少取得 workflowId/decisionId、当前行 revision、完整 question/status/flags/addressee、creator、关联票/正文指针、当前作者/来源，以及核对所需的明确用户答复/任务依据。移交候选另记录当前可见活动上下文/结论覆盖、历史来源缺口与通知基线；未暴露/无权读取的内部设置和外部状态明确为未知。需历史时按需读取当前权限范围内版本；创建时间不能由 history[0] 猜。只报告最小摘要，不把私人正文写入公开仓库。

以本次 awaiting=true 的集合 W 为主样本，先按用途再按证据分组，每条恰归一类：

| 类别 | 判定含义 | 推荐处置意图（本轮不执行） |
|---|---|---|
| U 用户仍未答 | 存在真实用户未决问题，当前仍需其答复 | 保留 pending-user；不要因关联任务已完成就代用户作答 |
| H 已定但承接未完整 | 用户/任务决定明确，至少一项残余承诺尚未被既有任务完整承接 | 先落实任务承接与指针；未移交继续保留兼容标记 |
| D 已落实但旧标记未清 | 依原任务标准有可核对完成依据，无其他未兑现事项 | 显式登记依据并清旧 await；不是按 status 词猜 |
| M 任务镜像 | 无仍待用户问题，全部残余行动已由明确既有任务/任务集合完整承接，额外 await 只是重复记账 | 明确“责任已移交任务，非完成声明”，再清旧 await；任务可仍在进行 |
| L 技术选择/事实日志 | 从来无需用户裁决且不承载未完成承诺 | 关键内容保留/指向已有文档，显式结束不适当标记；不追溯称旧写入非法 |
| R 已撤回/被替代 | 有明确撤回或替代依据，依赖动作已妥善处理 | 保留替代/撤回来源后显式收尾，不把“被替代”当已交付 |
| X 无法判定 | 缺正文/用户答复/任务依据、授权或状态冲突 | 保留原标记并列出具体缺口，未知不当已完成 |

优先级：缺少支持当前判断/处置所必需的关键证据归 X；已有依据可确定 U/H 时，不因外部完成状态未知就抹去该未决事实，另带证据未知标签。确仍需用户回答为 U（并另列残余行动）；R 仅指原承诺已全部撤回/由明确替代关系妥善承接，不遗留未转交动作；其余按原始用途归 L 或任务/承诺，再区分全部行动有完成依据 D、全部残余动作已由明确任务/任务集合完整承接且只是重复状态 M、尚需承接/落实 H。混合记录和部分完成不得归 D/L 来掩盖残余承诺。不要仅靠 pending、addressee、result 或自由 status 自动分类。

报告须给出 U+H+D+M+L+R+X=|W|；另外报告 raw pending、pending-user、pending-for-principal、raw awaiting 四种实际计数，以及 pending∩awaiting、pending-user∩awaiting、非用户 pending。令用户待答集合为 P，单列 W∩P 与 P\W，不把二者相加成总待办。current 对象数、history 版本行数与去重关联任务数分别报告，不把历史分页 total 当当前事项数。多票一事项只算一条 decision；非用户 pending 且不在 W 的事项另表，不漏报也不混入“88”。完整性/权限不足时只给已核下界和缺口，不能强配等式。核账分类是本次分析结果，不新增持久分类账/后台状态机。

### 6.2 当前实际数据入口与请求模板

[模型工具](<../src/host.ts#L1709-L1714>)绑定 caller.sessionId，本研究会话不能加一个 sessionId 参数读另一 owner。现有[用户 Remote](<../src/host.ts#L1289-L1302>)支持指定会话并 authorizeCaller，但本轮工具绑定没有该浏览器用户 RPC/凭据，不借底层存储、伪造 operator 或自授 assignment 绕过。设置页的选择导航不增加授权。

此处“只读”指不主动发 authored 业务/个人显示/上下文/清理变更，并非承诺零底层持久副作用。现有[历史查询入口](<../src/runtime.ts#L1314-L1324>)会正常补捕获衍生历史，普通会话读取也可能捕获/推进消费水位。若授权连这些副作用都禁止，先核验现有真正纯读表示；没有经证实的入口就停在可纯读范围，不绕底层读取。

可在目标会话由有权操作者发起下面的只读请求（不是自动任务，也没有在本轮执行；正常捕获副作用遵循上段约束）：

> 只读核对本会话裁决记录。先报告实际 owner/instance/scope、records/business 修订与当前 pending-user/awaiting 数；读完同源修订分页并按需核对正文、明确答复和关联任务。按本契约 U/H/D/M/L/R/X 分类 awaiting 集合，另报与用户未决重叠及非用户 pending。证据不足列 X，不猜已完成。只返回分类数量、必要标识/来源指针和建议，不写 put-decision/put-ticket，不改已读/隐藏/注入，不归档、不删除、不启动执行。没有权限或分页不完整时明确停止在已核范围，不声称核完 88。

## 7. 显式处置的顺序、失败与恢复（仅未来执行方案）

1. 先保留核账时的目标 ID 集合、四种原始计数/交集、原事项及三种修订、creator/可用来源覆盖、任务/上下文覆盖与通知基线；逐条列目标字段 before→after、残余未承接动作、责任归属或未知。在有权访问的上下文确定处置；不会因为发布新版自动执行。
2. H/M 若要移交，先确保明确的既有任务/任务集合实际存在、已记录全部残余承诺、原决定约束与必要答复/指针，且在实际任务/文档消费中仍可发现，不会在清 await 后一起退出活动上下文。保留原显式纳入/排除选择，不以自动 set-context=true 覆盖；不能确认有效承载时停在原标记。功能/权限不允许或写回执未知也先停，不能先清后补。引用已有任务需核对内容是否真的承接；任务创建/上下文调整/decision 写入是分步效果，不是原子事务。
3. 之后对原 decision 做一次显式 put-decision，保留必填 question/status、result 和其他有效字段，在 context 追加短处置说明、记录本次来源；只清有依据的 await。U 的 pending 不因移交清除；D/M/L/R 如仍存在其他真实未决也不能顺带清 pending。
4. 命令用原授权业务修订 CAS 与唯一 operationId。并发冲突先重读并核对原行/处置依据，不盲目升级修订重发草稿；其他变更不能被旧全量 value 覆盖。
5. 每个回执先区分业务应用事实与 historyCapture/notificationRecording 的失败或未知，不能把写成功冒称所有副作用成功，也不能因副作用失败重做业务。核对 appliedRevision 与当前 businessRevision 的不同职责，再读取目标当前值、仍保留义务与必要上下文承接。下一条使用其重新核验后的业务水位，不把历史查询修订、行修订或 appliedRevision 误作 businessRevision。
6. 区分失败类型：普通丢回执且来源健康时，先复核当前权限，再按同作者/同 payload/同 operationId 走现有幂等重放；撤权/关联变化则停止在未知，由有权入口核验，不换作者/ID 或绕底层。若是 storage-uncertain/indeterminate latch，则停止后续写，按[现行存储恢复](<../src/controls/versioned-storage.ts#L69-L88>)关闭并重新打开相应域、核对实际持久状态，不能仅换 wrapper/ID 或直接重放。业务已确认但输出/历史捕获/通知失败只恢复后半步，不重做业务；部分成功（任务已承接，decision 写失败）如实记录。现有多命令/外部 tracker 没有跨操作原子事务，不宣称 all-or-nothing。
7. 无批量清零/删除按钮、定时迁移器、keyword 自动消账；必要显式处置依现有任务/用户授权执行，不为每条再发一个“是否允许记账”的业务审批。
8. 回退 UI/引导版本不会回退已经写下的业务历史。处置错误通过有依据的新业务更新纠正，保留实际作者与历史；不可恢复整份旧文档覆盖并发工作，也不伪造旧时间。补偿标记不撤销外部任务或真实执行；不以 compact/purge 作回滚，已有清理正文/抑制覆盖不承诺无损恢复。当前业务未变的只读阶段可随时停止。

处置后报告逐条成功/冲突/未知/未执行以及待核原集合的去向，重读新的完整范围，说明新加入记录与并发变化；计数差额须逐 ID 解释，并发/新加入 cohort 单列，不以归零验收。本次处置不删除/覆盖原问题/答复；仅在当前授权与已保留来源范围内可追溯，历史已有清理缺口就明确报告，计数下降不冒称执行完成或总体任务完成。
